# Clean Installation Compatibility

The `linux-configuration` skill owns the clean-install and root-optional
installer rules; they are not restated here. Repository-specific installer
facts:

Keep Codex, Claude Code, Cline, Grok, opencode, marketplace registration, and
plugin defaults
reproducible through this repository's `install.sh` and the master
`installation_scripts/install.sh`. The committed `default.json` is the source
of truth for per-skill defaults and must never be gitignored. opencode provider
authentication is not managed here — it is left to opencode's own
`opencode auth login`; no API key is read or written by the installer.

This repository owns the raw Codex and Cline npm installations, the Grok CLI,
the opencode CLI (official installer, `~/.config/opencode` model/variant
defaults, `permission: allow` yolo mode),
generated
Codex/Claude marketplace catalogs, CLI marketplace registration, and plugin
installation. `claude_code_status_bar` owns the delegated Claude renderer;
`programming_prompts` owns only
per-plugin content and manifests. `claude_code_status_bar` owns all agent display
configuration, and Agent Command Center owns tracker/runtime behavior, the
tracking-aware Codex wrapper, and its Qwen3.8-27B local-model selection.

User configuration belongs under the target user's home and must preserve
unrelated settings and installed plugins.

The `opencode_cli` component only installs the opencode binary
(`~/.opencode/bin`, launcher `~/.local/bin/opencode`) and its
`~/.config/opencode` model/reasoning config. The `oca` (launch), `ocr` (resume),
and `ocac` (commit-mode) launchers are generated by Agent Command Center's
`agent_tracker` component, not this repo — so a change to opencode is not live
until both installers have actually run (`bash install.sh --select opencode_cli`
here, then `bash agent_command_center/install.sh --select agent_tracker`).
Verify integration work by running the installers, not by editing scripts alone.


## Shared workflow

This file intentionally contains project-specific ownership, data-safety,
component, integration, and deployment facts. The reusable workflow rules
live in the selected skills and must not be copied into every project file.

Before editing, read this project file, then load:

- `general-programming-guidelines` for the engineering workflow;
- `commits` for capability boundaries and commit verification;
- `worktree` for isolation, branch, merge, and consumer reapplication; and
- `linux-configuration` when the task touches GNOME, desktop settings,
  systemd user services, or any `install.sh`.

Those skills are the cross-project source of truth for workflow, delivery,
desktop deployment, clean-install compatibility, and root-optional installer
rules. Project-specific sections here may narrow ownership or add required
verification, but must not restate or contradict those shared policies.
